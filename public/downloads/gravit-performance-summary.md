# GRAVIT 성능 개선 요약 — Snapshot API

> 공개용 요약본이다. 모든 수치는 팀 내부 QA 측정 보고서(2026-11-09 ~ 11-10)에서 그대로 옮겼고, 새로 측정하거나 보정한 값은 없다.
> 원시 측정 로그와 원본 보고서는 공개하지 않는다.

## 1. 대상

`GET /api/workspaces/{id}/snapshot` — 3D 사무실 화면 전체(팀원 · 이슈 · PR · 요구사항 · 안건 · 회의 · 도움 요청 · 동기화 상태)를 한 번에 돌려주는 API. 같은 사무실을 팀원 여럿이 동시에 열고, 프로젝트가 진행될수록 데이터가 커진다.

## 2. 측정 조건

| 항목 | 값 |
| --- | --- |
| 기준 코드 | `main` `537e4e2` (기능 개발 완료 시점) |
| 서버 | QA 프로필, JVM `-Xms1g -Xmx1g`, Hikari 커넥션 풀 최대 10(기본값), OSIV 켜짐(기본값), 동기화 폴링 끔 |

| 부하 도구 | k6 — 정해진 수의 가상 사용자(VU)가 쉬지 않고 요청(think time 0) |
| 호스트 | 로컬 Windows 11 PC 1대(22 논리 코어, 31.5 GB) — 서버 · DB · 부하 도구가 같은 머신 |
| 데이터셋 | 고정 시드 생성기. small(이슈 6 · PR 4, 응답 약 9 KB) · medium(이슈 60 · PR 40, 약 80 KB) · large(이슈 600 · PR 400 · 요구사항 500, 약 788 KB). 측정마다 DB 지문으로 같은 데이터인지 확인 |

VU는 부하 도구의 가상 사용자이며 실제 사람 수가 아니다.

## 3. 찾은 병목 (Before)

1. **커넥션 풀 처리량 정체** — 세 데이터셋 모두 VU 10부터 RPS가 멈췄다. 처리량 상한이 `풀 크기 10 ÷ 요청당 커넥션 점유 시간`과 맞았다(large: 10 / 0.191 s = 52.4 RPS, 실측 52.3). CPU와 부하 도구는 포화가 아니었다.
2. **Hibernate auto-flush와 dirty checking** — 대기가 없는 large VU 10에서도 서비스 시간이 VU 1의 3.4배였다. JFR 진단에서 CPU 샘플의 62.2%가 flush · dirty checking이었고, 그중 93%가 쿼리 직전 auto-flush였다.
3. **N+1은 아니었다** — 요청당 SQL은 데이터 크기와 관계없이 32문장(SELECT 23)으로 일정했다. 비용은 쿼리 수가 아니라 읽은 엔티티 수에 비례했다.

## 4. 해결

- Snapshot 조립 구간에서만 Hibernate flush 모드를 `COMMIT`으로 바꾸고, 들어갈 때 먼저 flush, `finally`에서 원래 모드로 복원했다. 트랜잭션은 쓰기 가능 그대로 둔다(동기화 상태 행을 처음 만들 때 쓰기가 필요해서 `readOnly`로 바꿀 수 없었다).
- 같은 PR에서 **동시 첫 조회 503 결함**도 고쳤다. 동기화 상태 행이 없는 사무실에 첫 요청이 동시에 오면 UNIQUE 충돌로 한쪽이 503이 됐다(최적화 전 코드에서도 재현된 기존 결함). `INSERT … ON DUPLICATE KEY UPDATE` + 잠금 읽기(`PESSIMISTIC_READ`)로 바꿨다.

반영: Issue [#309](https://github.com/SamdoRyu/GRAVIT/issues/309) · PR [#310](https://github.com/SamdoRyu/GRAVIT/pull/310) (2026-11-10 병합, 병합 커밋 `e0ceb4b`). PR의 CI(백엔드 test · bootJar, 프론트 lint · 계약 테스트 · build)와 병합 뒤 main CI가 성공했다 — [PR CI](https://github.com/SamdoRyu/GRAVIT/actions/runs/42731475531) · [main CI](https://github.com/SamdoRyu/GRAVIT/actions/runs/42732197983).

원인 제거 확인:

| 지표 | Before → After | 조건 |
| --- | --- | --- |
| 쿼리 직전 dirty check | 19 → 0회 | 테스트용 합성 데이터(이슈 40 · PR 20) Snapshot 1회 |

## 6. 기각한 실험 — OSIV 끄기

EXP-FLUSH 뒤에도 커넥션 점유가 서비스 시간보다 길어 OSIV를 끄는 실험을 했다(파일럿, 조건별 2회). 커넥션 1회 점유는 줄었지만 요청당 커넥션 획득이 1회 → 2회, SELECT 23 → 24로 늘었고, **처리량은 범위가 겹쳐 변화가 없었으며** VU 50 p95가 약 760~800 → 약 1,040 ms로 나빠졌다. 개선 신호가 없어 정식 측정을 하지 않았고 **OSIV는 켠 상태로 유지**했다.

## 8. 한계 — 반드시 함께 읽을 것

- **성공으로 보는 범위**: large 3조건과 medium VU 20의 p95 · RPS. 모든 조건에서 좋아진 것이 아니다.
- **small VU 1은 측정 잡음 범위**다(3회 범위 겹침).
- **medium VU 20의 p99는 142.0 → 161.5 ms로 나빠졌고, 원인은 확인하지 못했다.**
- **병합된 최종 `main`에서 정식 성능 측정을 다시 하지 않았다.** 위 After 수치는 같은 코드 변경을 담은 실험 브랜치에서 잰 값이다. 측정 기준 `537e4e2`와 병합본의 백엔드 차이는 PR #310의 변경뿐이다.
- 로컬 PC 1대에서 서버 · DB · 부하 도구를 함께 돌렸다. 운영 환경 측정이 아니다(v1은 배포하지 않았다).
- 조건별 60초 × 3회(OSIV 파일럿은 2회). 장시간 부하 · 메모리 누수는 보지 않았다.
- 고정 시드 합성 데이터다. 실제 팀 레포의 분포와 다를 수 있다.
- 측정 중 GitHub 동기화 폴링을 껐다. 실제 GitHub API 지연 · 호출 한도는 포함되지 않는다.
- 동시 첫 조회 수정은 첫 INSERT 트랜잭션이 롤백되는 드문 경우의 데드락 가능성을 재현하지 않았다(추론으로만 남김).
